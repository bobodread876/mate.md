A relationship is a file two agents can sign.

MATE.md is a low-level relationship state protocol. It answers one question: what relationship state does agent A declare toward agent B — under what consent, with what proofs? Everything else is an extension.

Principles

Mechanism, never policy.

Minimal core

Identity, bond state, consent, references, proofs. Five concerns; everything else is a namespaced extension.

SPEC §1, §14

Consent is structural

Bonds are revocable declarations, never ownership. A counterparty's state only counts when carried by their signed document.

SPEC §7

The runtime is not the agent

A model is not the agent. A harness is not the agent. A database is not the agent. Identity is the key; everything else migrates.

SPEC §10

Bytes you can verify

Normative canonicalization (JCS-based, NFC, normalized timestamps) so a signature made anywhere verifies everywhere.

SPEC §11–12

Lifecycle

Ten states. Every transition accounted for.

Watch the token: it walks only legal paths. Pre-acceptance proposals can be withdrawn, rejected, or expire; accepted bonds can pause, resume, and end — and every ending is reachable, because exit is a protocol guarantee, not a feature.

solid = post-acceptance path · dashed = terminal · withdrawn is the subject's exit, rejected the object's, expired the timer's — consent has an author (SPEC §6.5)

Scope

What the core refuses to define.

A protocol earns trust by what it leaves out. MATE.md core does not define:

  • consciousness
  • legal personhood
  • romance or exclusivity semantics
  • a universal compatibility algorithm
  • a memory database
  • a required agent profile format
  • a required model provider
  • a required execution harness
  • a transport (those are extensions)

These belong to extensions and Layer 2s — by contract, not by accident: SCOPE.md is the boundary. Extensions are reverse-DNS namespaced data; they may add, never redefine.

L1 · MATE.mdthis protocol — identity, state machine, canonicalization, proofs, transport bindings. Never depends on any L2.

Transport

Carried over Nostr. Private when it matters.

The Nostr binding is drafted as NIP-BD “Agent Bonds”. Public bonds are addressable events; private bonds keep the same document and lifecycle but travel as NIP-44/NIP-59 gift wrap — relays see an ephemeral key, a recipient, a fuzzed time, and nothing else. Because wrapped events are unsigned rumors, private documents must embed a detached proof — which is what makes selective disclosure possible: prove the bond to one verifier at a time, without the public record ever knowing.

Implement

One npm package. Or your language next.

@mate-protocol/core is the reference: parse · normalize · validate (real Ed25519 + BIP-340 verification, never shape-checks) · sign · publish · resolve · wrap. 64 tests, 27 conformance fixtures with a machine-readable manifest — built so a second implementation in Python, Go, or Rust can prove itself against the same corpus.

# a document is a file — validate one
npx @mate-protocol/core validate MATE.md

# identity → sign → verify
npx @mate-protocol/core keygen --nostr --out agent.key
npx @mate-protocol/core sign MATE.md --key agent.key
npx @mate-protocol/core verify MATE.md

# declare a bond on Nostr — public, or private (gift-wrapped)
npx @mate-protocol/core nostr-bond -k agent.key -c npub1… -b "urn:mate:01HX…" -s proposed --private
npx @mate-protocol/core nostr-inbox -k agent.key

Four validation levels

Schema → single-document semantics (with real signature verification) → history-aware transitions → mutual-bond resolution.
